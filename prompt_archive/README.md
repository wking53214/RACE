# RACE PROMPT ARCHIVE AND LEARNING SYSTEM

## 1. Purpose

Preserve every material prompt generated by RACE, evaluate its execution, capture lessons, and support evidence-driven improvement of future prompts.

The archive is RACE's institutional memory for prompt engineering.

## 2. Four Functional Areas

### Prompt Archive
Preserves exact generated prompts, their versions, source inputs, and generation context.

### Prompt Evaluation
Records execution results, strengths, weaknesses, failures, and deviations.

### Learning Register
Captures reusable lessons from individual prompts and campaigns.

### Prompt Evolution
Tracks proposed, approved, implemented, and validated improvements.

## 3. Directory Organization

- campaigns/: Campaign-specific prompt records.
- templates/: Standardized archive, evaluation, and learning formats.
- learnings/: Individual learning records and index.
- PROMPT_RECORD_SCHEMA.md: Required record fields and rules.
- LEARNING_REGISTER.md: Central learning index and status.
- PROMPT_EVOLUTION_LOG.md: Approved and proposed prompt improvements.

## 4. Prompt Identification

Use this naming convention:

CAMPAIGN-PHASE-SEQUENCE-VERSION

Example:

HERALD-P0-001-v1
HERALD-P1-001-v1
HERALD-P2-001-v1

Each version receives its own directory containing:

- PROMPT.md
- RECORD.md
- EVALUATION.md

PROMPT.md must preserve the exact generated prompt.

RECORD.md documents the prompt's origin and intended use.

EVALUATION.md records actual execution results after execution.

## 5. Immutability

Archived prompt versions must never be silently overwritten.

A substantive revision creates a new version.

Preserve earlier versions so that performance and changes can be compared.

Corrections to archived records must be documented rather than silently replacing historical evidence.

## 6. Required Lifecycle

1. Generate a mission-specific prompt.
2. Assign its unique identifier.
3. Archive the exact prompt.
4. Complete its generation record.
5. Review and authorize execution as required.
6. Execute the prompt.
7. Record actual results.
8. Evaluate performance.
9. Create learning entries where justified.
10. Submit proposed improvements for human review.
11. Record approved changes and subsequent validation.

Do not represent an unexecuted prompt as evaluated.

## 7. Learning Integrity

Distinguish:

- OBSERVED: Directly supported by cited evidence, including execution results or direct inspection.
- INFERRED: A reasoned explanation not yet established.
- PROPOSED: A suggested improvement.
- VALIDATED: An improvement tested against defined criteria.

One campaign's experience does not automatically establish a universal rule.

Look for recurring patterns across campaigns where possible.

## 8. Human Governance

RACE may identify weaknesses and recommend improvements.

It may not silently change its governing instructions, schemas, templates, or evaluation standards.

Changes require explicit human authorization and a recorded disposition.

## 9. Data Protection

Do not archive passwords, access tokens, private keys, credentials, or unnecessary sensitive personal information.

Sanitize input snapshots while preserving the information needed to understand prompt generation.

Use references or hashes for large external artifacts where appropriate.

## 10. Governing Rule

Preserve what RACE generated, record what actually happened, learn from evidence, and improve only through traceable and authorized changes.
